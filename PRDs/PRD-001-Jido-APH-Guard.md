## 0. TL;DR for a claiming agent

`jido_aph` is a small reusable Elixir library plus a thin demo, showing two jido v2.3 agents exchanging an **APH-notarized action request** and a gate that refuses everything else. **Scribe** (acting on behalf of a human) attaches the aph repo's golden envelope — `examples/principal_signed_envelope.json` (channel.kind `slack`, contentClass `Reply`, attestationMode `PrincipalSigned`, embedded delegationMandate, bodySize 427) — to a `slack.reply.requested` signal via a registered `Jido.Signal.Ext` (namespace `aph.notarization.v1`, the documented mirror of the A2A metadata key `aph://extensions/notarization/v1`). **Gateway** mounts the `JidoAph.Guard` plugin (`required: true, require_mode: "PrincipalSigned"`), whose `prepare_signal/2` hook gates every routed signal through the parity-locked four-op `aph-ex` NIF **before any Action runs**: size bound → strict parse → mode gate (APH_E012) → proof-structure (APH_E013).

The guard's verdict wording is fixed: **"notarization-shaped, mode policy satisfied"** — the words "verified" and "signed" never appear in its output, because an aph-ex pass "says NOTHING about whether any signature verifies" (`lib/aph.ex`, quoted verbatim in our README). Real cryptographic depth (all four Ed25519 signatures over JCS/RFC 8785, issuance order, embedded-mandate binding, validity window, bodySha256 over received bytes, closed vocabulary — spec §8.3) is demonstrated by an **optional** demo leg that shells the independent TypeScript implementation (`../aph/interpreters/typescript`, Node >= 20) behind a `JidoAph.DeepVerifier` behaviour seam. The deep leg is offline — the TS implementation never fetches — with exactly ONE key supplied out of band: the golden's `did:web` notary key, re-derived from the published RFC 8032 §7.1 TEST 3 vector (every other signature verifies under `did:key` material that travels in the envelope itself), and the transcript states that key-sourcing story out loud. The demo's teaching climax is the **depth-split beat**: a structurally perfect envelope with a fake proofValue passes every guard check and is then refused by the deep leg on signature verification — this is why structural validity is never called verification.

Scenario is fully v0.1-conformant (slack/Reply from the closed §7.1.5/§7.1.6 enums), zero dependency on RFC 0002, zero placeholder fields. Governance is two cards: the maintainer notification (T2) goes out at the START of the build — this repo is exactly the artifact class that expires the aph pre-production exception (CONTRIBUTING.md), and its four design questions feed D2/D7 while the work is still cheap to steer — and the acknowledgment gate (T17), which was **blocking before publish**. That gate cleared on 2026-08-27: publication was authorized in draft status and question (d) was answered (D2 → `aph-jido`), while (a), (b) and (c) remain open and are recorded as open, (c) still governing D7.

## 1. Problem & why now

APH v0.1 defines how an agent's act on behalf of a human is cryptographically notarized and how a counterpart agent verifies before acting (spec §8.3), and the A2A extension (`spec/a2a-extension.md`) defines how the envelope rides agent-to-agent traffic. What does not exist anywhere: a worked example in a real agent framework showing the **consumer side** — one agent presenting an envelope, another refusing to act without one. jido (Elixir/OTP, v2.3.x) is the natural first host: aph already ships an Elixir binding (`aph-ex`, a rustler NIF over the Rust reference), and jido's plugin pipeline has a hook (`prepare_signal/2`) documented for exactly this job — "verifies, decrypts, or canonicalizes signals before routing."

Why now, and why carefully: the aph repo's discipline treats an overclaim as poison, and the single hardest design question — **how does the verifier agent verify honestly when the only BEAM-native surface stops at structural depth?** — has a clean answer today (guard at depth 0–1 + mode policy, independent TS implementation for full §8.3, an explicit behaviour seam between them) that gets harder to retrofit once a sloppier example exists in the wild. Shipping this is also the event that expires aph's pre-production spec exception, so it must be done with the governance gate built in, not bolted on.

## 3. The demo story (what a reader runs and sees)

Setup: clone `aph` and `jido_aph` as siblings; Elixir 1.18 / OTP 27 / Rust toolchain (the aph-ex NIF's prebuilt `.so` is gitignored upstream — a Rust toolchain is mandatory, and the README never promises otherwise). Optional for the deep leg: Node >= 20 and `npm install && npm run build` in `../aph/interpreters/typescript`.

`mix demo.run` (no Node required) prints, in order:

1. **Provenance banner** — the pinned sibling-aph SHA and the golden fixture's identity (bodySize 427 pin), so every claim below is attributable to exact bytes.
2. **Happy path** — Scribe attaches the golden envelope (verbatim JSON text) + base64 of `principal_signed_body.txt` to `slack.reply.requested`; Gateway's guard admits it and `DeliverReply` logs `would deliver (no channel adapter)`. The transcript enumerates, per leg, **exactly which checks RAN** (§7.1.7.1 byte bound, §8.3 step 1 strict parse, §8.3.1 step 1a mode gate, §7.1.11 proof structure) **and which did NOT** (signatures, key discovery, validity window, revocation, bodySha256, closed vocabulary). Verdict wording: `notarization-shaped, mode policy satisfied (PrincipalSigned)`.
3. **Refusal matrix** — six rows, tampered variants derived in-memory at runtime (committed signed fixtures are never text-edited; derived negatives are never committed):
   - missing extension under `required: true` → reject + log, mirroring a2a-extension.md §5;
   - forged `PrincipalSigned` label → `APH_E013` (§7.1.11 — label must match structure in both directions);
   - mode-absent envelope (`slack_reply_envelope.json` — absent normatively means NotaryAttested, §7.1.7) against a `PrincipalSigned` policy → `APH_E012`, no silent downgrade; the narration describes its `AskEveryTime` decision field as the human's standing CONFIGURATION, never a per-act verdict (§7.1.7 — implementations misreading this "have shipped real defects");
   - unknown envelope field → strict-parse refusal, no APH code (§8.3 step 1);
   - > 64 KiB envelope → refused **before** any parse (§7.1.7.1 bounds — canonicalization happens on unauthenticated input);
   - bare signal under `required: false` → passes through **tagged unverified** (the messaging-side "deliver flagged as unverified").
4. **Honesty footer** — the not-checked list, verbatim, machine-asserted in CI.

`mix demo.deep_verify` (optional, Node >= 20) then:

5. Runs the TS sidecar (`verifyEnvelope` from `../aph/interpreters/typescript`) on the same envelope with a **pinned `now`** inside the fixture's 2026-05-21→22 validity window and a `keys` map supplying exactly ONE out-of-band key — the golden notary's Ed25519 public key under `did:web:notary.squillo.com#key-1`, re-derivable by anyone from the published RFC 8032 §7.1 TEST 3 vector (per `examples/README.md`; the TS implementation never fetches, and resolves non-did:key methods only from `options.keys`). The transcript says out loud that `now` is pinned because the fixture's window is fixed, not because time is negotiable, and states the key-sourcing story: one notary key handed in, everything else verified under `did:key` material traveling in the envelope itself. Reports `bodyHashChecked: true`, `embeddedMandateChecked: true`.
6. **Wall-clock beat** — runs once against real current time and shows the validity-window refusal (§8.3 time-window step; APH_E003 in the §11 taxonomy), explaining why the pin exists instead of hiding it.
7. **Depth-split beat** (the single best teaching moment): a runtime-derived, structurally perfect PrincipalSigned-shaped envelope with a fake proofValue passes EVERY guard check, then the deep leg refuses it on signature verification. Narration: "this is why structural validity is never called verification."
8. Prints what this leg ADDS (all signatures over JCS, §7.2.1 issuance order, embedded-mandate binding §7.1.7.1/§8.3.1 step 1d, window, bodySha256 over received bytes, closed §7.1.5/§7.1.6 vocabulary) and what it STILL does not do (network key discovery — the TS implementation never fetches, which is exactly why the notary's did:web key had to be handed in; revocation — the golden carries no credentialStatus and TS refuses status-bearing envelopes; live notary — never contacted).

## 5. Non-goals

- **No new aph-ex ops.** The binding surface is parity-locked at exactly four ops across Elixir/wasm/Python; nothing here grows, wraps-and-extends, or forks it.
- **No cryptography in Elixir** — including no `:crypto.hash` on any trust path; even SHA-256 is delegated to the sidecar (the §8.3 step 8 culture question goes to the recorded maintainer ruling — T2 asks, T17 records).
- **No service/database-mutation scenario.** RFC 0002's `service` channel kind is not in v0.1; `examples/a2a-database-change/` is referenced only as the honest non-conformant precedent, never imitated. This demo takes zero placeholders.
- **No real A2A HTTP, no AgentCard served or fetched** — jido CloudEvents signals are the rail; the carry pattern and `required` semantics are mirrored, and the README says so.
- **No real Slack delivery, no channel adapter** — channel.kind names the end-delivery medium (§1.1.1); the demo stops at the gate with "would deliver".
- **No live-notary, key-discovery (§8.4), or revocation transport** — the deep leg is offline: nothing resolves, nothing fetches. The principal side is `did:key` (decoded from the identifier itself); the golden's one non-did:key key — the `did:web` notary's — is supplied out of band from the published RFC 8032 §7.1 TEST 3 vector, and the transcript says so.
- **No minting** — envelopes are pre-minted committed goldens; the demo never claims its own run was humanly authorized.
- **No hex.pm publish** — the path dep makes it impossible and unclaimed names are not reserved (owner action, out of scope).
- **No Rust sidecar over crates.io aph-core, no guard-integrated `depth: :deep` runtime** — named follow-on PRDs, deliberately staged out.
- **No wasm route** — identical four ops to the NIF at strictly worse cost for a BEAM host; excluded.

**D3 — Dependency shape.** Recommendation: sibling-clone path dep on `../aph/interpreters/elixir` (aph-ex is not on hex.pm — confirmed 2026-08-27 — and its README says unclaimed is not reserved). What flips it: aph-ex actually publishing to hex.pm (owner action), at which point the path dep becomes a version dep in one commit.

**D4 — Scenario.** Recommendation: fully v0.1-conformant slack Reply built on `examples/principal_signed_envelope.json` (+ `principal_signed_body.txt`). Chosen for: its §7.3.1 worked-example pedigree (the spec's prose and this file describe the same credential); its separate git-tracked 427-byte body file, which makes the demo's `body_b64` carry — authorized bytes traveling verbatim, hashed as received — real rather than notional (sha256 of the tracked file equals the envelope's `bodySha256` `dae0b23f…`); and its pinning in the upstream Elixir suite. The trade-off, stated: its notary is `did:web`, so the deep leg supplies that ONE key out of band (D5/T12) — this is not "the only fixture that verifies completely offline"; `examples/ts_minted_envelope.json` (both parties `did:key`, real body binding over its in-file preview, upstream's designated "easiest first target for a stranger's verifier") is the zero-key-config alternative and remains available as a second demo row, never a silent replacement. (Upstream `examples/README.md` currently calls ts_minted the ONLY file with a real body binding; that line is stale — the golden's binding is byte-real — and the T2 erratum reports it.) What flips it: nothing in PRD-001. A service-act leg becomes thinkable only after RFC 0002 lands upstream, as a follow-on PRD.

**D5 — Deep-verification route.** Recommendation: the independent published TypeScript implementation's `verifyEnvelope` (the only published full-§8.3 surface — in Rust the assembled algorithm is conformance-harness test support, not API), demo-owned, behind the `JidoAph.DeepVerifier` behaviour. What flips it: aph publishing a full-§8.3 API from aph-core/aph-cli, at which point a Rust sidecar becomes a follow-on PRD implementing the same behaviour.

**D6 — Envelope carry.** Recommendation: a registered `Jido.Signal.Ext` with namespace `aph.notarization.v1` carrying `envelope_json` (required string — JSON text, never a decoded map on the trust path) + `body_b64` (optional string — authorized bytes travel verbatim). The A2A URI cannot be a jido namespace (the namespace regex forbids `:` and `/`), so both identifiers live as single module-attribute constants with a byte-exact documented mapping. What flips it: a jido_signal namespace-rule change, or a real A2A HTTP leg (out of scope here).

**D7 — Corpus consumption.** Recommendation: read goldens from the SHA-pinned sibling clone at runtime via an `Application` config key (`:aph_repo_path`, default `"../aph"`), with a loud raise naming the sibling-clone requirement — runtime config over compile-time path resolution, because compile-time `Path.expand` misdepth is the documented silent-failure gotcha and runtime config makes CI's pinned-checkout layout trivial. What flips it: the maintainer ruling (T2 question c) preferring vendored copies of the vectors — aph-conformance's own docs say copying vectors is the point, so this may flip cheaply.

## 7. Architecture

### 7.1 Two layers, one seam

**Library:**
- `JidoAph.Signal.Ext.Notarization` — `use Jido.Signal.Ext, namespace: "aph.notarization.v1"`, schema `envelope_json` (required, `:string`) + `body_b64` (optional, `:string`). Unavoidable even for the thinnest demo: `Jido.Signal.put_extension/3` requires a compile-time-registered Ext module and validates against its schema.
- `JidoAph.Guard` — `use Jido.Plugin, name: "aph_guard"`. All verification in `prepare_signal/2`, refusing before any Action runs. Gate order, fixed and complete, all steps mandatory:
  1. `byte_size(envelope_json) <= 64 KiB` — **before any parse** (§7.1.7.1: canonicalization happens on unauthenticated input);
  2. `APH.parse_envelope_json/1` — strict, unknown fields denied (§8.3 step 1);
  3. `APH.require_attestation_mode/2` when `require_mode` configured (§8.3.1 step 1a; `APH_E012`; absent mode normatively means NotaryAttested — §7.1.7 — so a PrincipalSigned policy refuses it up front, no silent downgrade);
  4. `APH.verify_proof_structure/1` — **always**, even with no mode policy, because the mode gate alone admits a forged PrincipalSigned label (§7.1.11; `APH_E013`). A mandatory test proves exactly that admission-then-catch.

  Refusals matched by code prefix (`{:error, "APH_E012" <> _}` etc.); aph-ex messages passed through untouched; shape refusals carry the serde message and no code. Config: `required` (true = reject-and-log on missing extension, the a2a-extension.md §3/§5 `AgentExtension required:true` mirror; false = pass through tagged unverified), `require_mode` (`nil | "PrincipalSigned" | "NotaryAttested"`), `signal_patterns`, `refusal` (`:refuse_and_log` in v1), `depth` (`:structural` only; config validation rejects `:deep` unless a `deep_verifier` module is supplied — which nothing in-library provides).
- `JidoAph.DeepVerifier` — behaviour only: `@callback verify(envelope_json :: String.t(), opts :: keyword) :: {:ok, map} | {:error, term}`, opts documented to include `:body_bytes`, `:now`, `:require_mode`. The moduledoc names the two known implementation routes (TS sidecar; Rust sidecar over the published crates) and states both live OUTSIDE this library — the parity lock is untouched.
- Deliberately **no `prepare_emit` auto-attach**: an envelope notarizes one specific act and body; blanket attachment of a static envelope to every outbound signal would misrepresent what notarization asserts. Presenters attach explicitly per act.

**Demo:** `Demo.Jido` (`use Jido, otp_app: :demo`) supervised; Scribe and Gateway agents; `Demo.Actions.RequestSlackReply` and `Demo.Actions.DeliverReply`; delivery via `Jido.AgentServer.call` / `emit_to_pid` — never `emit_to_parent` (nil for standalone agents). `Demo.DeepVerifier.TsSidecar` implements the behaviour by `System.cmd` to node with `priv/node/verify.mjs` (~25 lines) over the sibling TS dist, passing the pinned `now`, `requireMode`, `bodyBytes`, and the one out-of-band notary key (D4/T12).

### 7.2 The signal-carry pattern (URI <-> namespace mapping)

The A2A extension carries the envelope inline under `Message.metadata["aph://extensions/notarization/v1"]` (`spec/a2a-extension.md`; `examples/a2a-database-change/a2a-message-send.json` is the wire precedent). jido signals mirror this with the registered extension namespace `aph.notarization.v1`, because jido namespaces must match `^[a-z][a-z0-9]*(?:\.[a-z][a-z0-9]*)*$`. Discipline:

- The A2A URI literal appears **exactly once under `lib/`**, as a module attribute, never built from substrings (a2a-extension.md's byte-exact-match rule) — enforced by a self-grep test scoped to code: the Ext moduledoc's mapping table interpolates the attribute rather than respelling it, and documentation occurrences (README, this PRD) sit outside the exactly-once scope but must byte-match the constant.
- The envelope crosses every boundary as JSON text in the extension's required string field, preserving aph-ex's JSON-in/JSON-out boundary; the untagged proof union is decided by the bytes, never by BEAM terms.
- Authorized body bytes travel verbatim as base64 in the same extension; bodySha256 is only ever recomputed over those received bytes, never a re-serialization (§8.3 step 8 — two JSON texts that parse equal can hash differently).
- The serialized wire shape of a signal carrying the extension is **pinned by a byte-level test before** the README documents the mapping to the A2A carry pattern (jido's `flatten_extensions` default shape is undocumented — we pin, we do not guess).
- The README states plainly: jido signals are the rail here, not A2A HTTP; guard `required: true` mirrors AgentCard `AgentExtension required: true` semantics, including the `required: false` "deliver flagged as unverified" path.

## 8. The honesty contract

Inherited from `examples/README.md`'s discipline: every claim is graded to exactly what each layer earns, and an overclaim is poison.

**What the guard claims:** the signal carries a notarization-shaped envelope (strict parse, §8.3 step 1), its proof structure matches its label in both directions (§7.1.11), and the configured attestation-mode policy is satisfied without downgrade (§8.3.1 step 1a). Fixed verdict wording: **"notarization-shaped, mode policy satisfied"**. Its logs never contain the bare words "verified" or "signed" — asserted by test.

**What the deep leg claims:** the same envelope independently passes full offline §8.3 in a second implementation — all signatures over JCS, issuance order, embedded-mandate binding, bodySha256 recomputed over the received bytes, closed vocabulary, and the validity window **against a pinned instant, and it says the instant is pinned** — with exactly one key supplied out of band (the golden notary's, from the published RFC 8032 §7.1 TEST 3 vector) and the transcript stating that too.

**What the example refuses to claim, anywhere:**
- that the guard "verifies" envelopes or that "the human signed this" — the README quotes aph-ex verbatim: a structure pass "says NOTHING about whether any signature verifies";
- that a service/database-mutation act can be notarized under v0.1 (RFC 0002 and `examples/a2a-database-change/` are the honest precedent, referenced, never imitated);
- that the rail is A2A HTTP, that any AgentCard is served or fetched, or that anything reaches Slack;
- that key discovery, revocation, or the live notary are exercised — the illustrative `did:web:notary.squillo.com` is the golden's notary `verificationMethod`, so it rides inside the fixture bytes on every signal the demo emits; it appears otherwise only in `verify.mjs`'s `keys` map and in the prose explaining that its key is supplied out of band, and it is never presented as live or resolvable; the live surface `did:web:aph-notary.squillo.com` is named only to say it is not contacted;
- that validity holds at wall clock (the fixture's 2026-05-21→22 window is past; the pin is stated and the wall-clock refusal is demonstrated);
- that the demo's own run was humanly authorized (envelopes are pre-minted goldens; nothing is minted);

## 11. Risks

- **Toolchain squeeze (existential):** jido requires Elixir ~> 1.18 while aph-ex's rustler ~> 0.30.0 pins were floor-tested at 1.13; if the NIF fails to compile on 1.18/OTP 27 the whole design blocks on an upstream aph-ex decision. T1 front-loads the spike; the pins are upstream-owned and never patched here.
- **jido 2.3.x under-documentation:** prepare_signal's refusal/halt contract, Zoi-vs-NimbleOptions schema acceptance, and flatten_extensions' serialized shape are unpinned in docs; T3/T5 pin them by test, but a jido point release can shift them — the pins fail fast and loudly.
- **Sibling-clone coupling:** tests and the deep leg read `../aph` at runtime/build; upstream fixture regeneration or verification-surface changes (the class `require_closed_vocabulary` — landed upstream as `c73a64c` during research — belongs to) can break CI. Mitigated by the SHA pin + drift gate, at the cost of deliberate bumps.
- **Governance timing:** publishing this repo expires the aph pre-production exception the moment it ships; skipping T2/T17 or going public early violates the exact discipline the example demonstrates. **Retired 2026-08-27** — the notification went out at build start as planned, and publication happened only after the acknowledgment was recorded (T17, `docs/governance/`). One residue remains, disclosed rather than closed: only question (d) was answered, so (c) can still change D7 after the fact, which is a weaker position than answers-before-build would have given.
- **Fixture window drift:** the deep leg's pinned `now` must track the golden's validFrom/validUntil if the fixture is ever re-minted upstream; the drift gate plus the bodySize pin turn a silent regeneration into a named failure.
- **Scope-creep pressure:** guard-integrated deep verification via Port, revocation-vector demonstration (aph-conformance's gzip status documents), and a Rust sidecar over crates.io are all natural next asks and all deliberately staged out; if they leak into PRD-001 the "thin demo" claim dies. §5 Non-goals is the defense.
- **Naming/affiliation:** the `jido_` prefix may read as an official agentjido package; the README disclaimer mitigates and T2 question (d) gets the name signed off (recorded at T17) before publish, when a rename is still cheap.
